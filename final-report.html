WHAT ACTUALLY HAPPENED WITH RELEASE 4.2

THE PLAIN VERSION

On 12 Aug 2026, Dispatch shipped three changes at once: it weighted proximity up and recent-acceptance-history down in the ranking formula, it cut the callout timeout from 90 seconds to 60, and it added a cosmetic console filter fix. Afterwards, callout tickets ran about 3× normal, and the acceptance rate — the headline number everyone watches — looked like it dipped and then came back.

It didn't come back. Four responders — Farlight, Meteor Mite, The Undertow, and Vesper — collapsed from ~12 offers a week to 0–1, and dropped almost entirely out of the weekly average. The other twelve responders absorbed their volume, which is why the pooled number looked like it recovered. The real, per-responder average never did.

POOLED ACCEPTANCE (the number everyone was shown)0.77 → 0.54 → 0.73
REAL UNWEIGHTED AVERAGE (what actually happened)0.59 — never recovered

That gap is the whole boss fight: a shield that looks like it regenerated, standing in front of four responders who took real, lasting damage.

DAMAGED, STANDING

Two of the four — Meteor Mite and Vesper — never filed a single support ticket. They only turn up in interviews. Vesper previously had one of the best acceptance records on the roster, which rules out "they were already struggling" as the explanation.

THE ACTUAL MECHANISM (not a hypothesis — read from the code)

Rook's scoring has exactly one way up and one way down, and they are not symmetric:

+0.08accepting a job (the only way up)
−0.12a decline OR a timeout — scored identically
0%decay over time — a 2019 TODO, never fixed

4.2 didn't create this trap — it just dialed the timeout down and the proximity weight up, which pushed a few responders low enough to fall into a hole with no floor. No logic changed in routing.py, offer.py, or history.py — just three numbers in config.py. Once ranked low, a responder gets offered less, which drops their score further, which gets them offered even less — and nothing in the code ever reverses it on its own.

LEVEL 3 — REWIND

FINDING: five independent agents, one converged answer

Five separate analytical lenses — code mechanism, tickets vs. data, interviews, redistribution patterns, timing — each built their own theory from this repo alone, then argued it out. All five landed on the same mechanism: the 4.2 rebalance plus a penalty that never decays, a self-reinforcing trap with no lens finding evidence for Priya's "it's just August" theory.

LEVEL 4 — X-RAY VISION

FINDING: the exact lines that break the trap open — and close it forever

Reading the code directly surfaced the asymmetric scoring: one function anywhere adds points (accepting a job, +0.08); a decline or a timeout — treated identically — subtracts 0.12, and nothing else ever moves a score back up. This is the single piece of evidence that turned "acceptance dropped" into "here's exactly why it can't recover on its own."

Find me the part of this code that takes points off somebody when they miss a ping or turn one down. Show it to me and explain it in plain English. Then find me every single thing in this code that puts points back on.

ITEM ACQUIRED

THE FIX: SECOND CHANCE

THE RULE

If a responder gets zero callout offers for 7 days, the very next callout that matches their capability tags and falls within a widened travel-range safety check goes to them first — no ranking math, regardless of where they currently sit. One real offer, guaranteed to arrive instead of maybe never arriving. It does not touch the 4.2 weights themselves, and it is not mutual aid, a quota, or a permanent override.

LIVE RIGHT NOW: THE MANUAL STOPGAP

Second Chance needs engineering time. This doesn't — a handler can trigger the same guarantee by hand, today, for the four responders who need it most. Built on real data from this repo, refined through two rounds of in-character feedback from the responders it's meant to help. Try it below:

Live prototype — 05-super-speed/guaranteed-offer-override.html

HOW WE'LL KNOW IT WORKED

Accepting a guaranteed offer only moves a score up by +0.08 — and the four stuck responders sit at 0.0–0.12. So the real check, a few weeks out, is whether they keep getting offered after the guaranteed one, not just the one courtesy job. If any of them take it and go quiet again, that's a sign the floor needs the no-decay code fix paired with it — not that Second Chance failed.

PERK UNLOCKED

WHAT KEEPS THIS BOSS FROM RESPAWNING

PERK 1 — investigate-and-prototype

The whole method used across Levels 1–5 — get oriented, read the evidence, reconcile what disagrees, read the mechanism, hypothesize, synthesize, give a confidence-scored recommendation, build and test a prototype, package it for a stakeholder — is now a saved skill, not a one-time run. It was put through a real eval: three test cases, run both with and without the skill.

100%pass rate WITH the skill
80%pass rate WITHOUT it
~2×time & token cost of using it

Without the skill, the same three gaps kept showing up: no stated numeric confidence, no named contradiction between a ticket and the real data, and no prototype produced at all — exactly the three things that made this investigation worth trusting.

PERK 2 — review-checklist

A fast, four-point structural pass on any brief before it goes to a stakeholder: does it name an owner, does it say how success will be measured, does the scope stay the same from the opening framing to the closing ask, and does it explain the problem before the fix. It already caught something real:

CHECKRESULT ON THE SECOND CHANCE BRIEF
Named ownerPartial — Wen named for engineering, not for the ask overall
Success criteriaFAIL — no way stated to tell later if it worked
Consistent scopePass — every addition explicitly flagged, nothing smuggled in
Problem before fixPass — two full sections of problem before the proposal

That one Fail is now fixed in the brief itself — the "How we'll know it worked" section above exists because this perk caught its absence.

PERK 3 — standing patrol

A recurring scheduled run, every Monday morning, applies review-checklist automatically to anything new or changed in the repo and reports back — a habit, not a one-off audit, so the next brief gets checked whether or not anyone remembers to ask.
